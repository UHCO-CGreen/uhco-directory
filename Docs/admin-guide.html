1. Getting Access

All admin accounts are created manually by a SUPER_ADMIN or a user with settings.admin_users.manage. There is no self-registration.

Login

You sign in with your CougarNet username and password at /admin/login.cfm. Credentials are validated against the CougarNet Active Directory (LDAP); no separate admin password is set. A Windows SSO option is implemented but currently disabled pending a production server configuration change.

What You Need Before You Can Log In

  • An AdminUser record must exist in the system with your CougarNet username.
  • That account must have at least one role assigned (or a direct permission grant) that includes admin.view.
  • Your CougarNet account must be active and non-expired in Active Directory.

Accessing the Admin

The UHCO Identity Admin can be reached via direct access.

  • Direct: https://portal.opt.uh.edu/admin/
  • MyUHCO V2: https://myuhco.opt.uh.edu/
    MyUHCO and UHCO_Identity share login credentials

Roles vs. Permissions

Access is controlled by two layers. Roles are named groups (e.g., USER_ADMIN, OD_STUDENT_ADMIN) that carry a set of permission keys. Permissions are the actual string keys checked throughout the application. You can also have individual permission grants or denials applied directly to your account on top of whatever your roles provide.

Scoped Roles

Several roles restrict which user records you can see and edit based on the user's flags and organization memberships. If you have a scoped role, users outside your scope are invisible to you across all list views, search results, and profile access.

2. Dashboard

The dashboard at /admin/ is your landing page after login. It requires admin.view.

It shows status badges for ongoing system health areas. The badges you see depend on your permissions:

  • Data Quality — shows the issue count from the most recent audit run. Visible to all admins.
  • UH Sync — shows how many pending diffs, gone, or new records were found in the last sync. Visible to all admins.
  • Duplicate Users — shows the number of unresolved candidate duplicate pairs. Visible to SUPER_ADMIN only.

Each badge links to its respective report. The dashboard also provides quick-navigation links to the main areas you have access to.

3. Managing Users

User management lives under /admin/users/. What you can do there depends on your permission grants and your role scope.

Viewing Users

Requires users.view. You can browse the directory, search by name or email, filter by tab (Faculty, Staff, Students, Alumni, Inactive), and open individual user profiles. Users outside your role scope are not shown.

Editing Users

Requires users.edit. You can modify a user's profile fields, names, contact info, titles, organizations, flags, external IDs, addresses, academic info, degrees, and bio. Creating new user records additionally requires the canCreateUsers policy check (tied to unrestricted roles).

Deleting Users

Requires users.delete. Hard-deletes the user record and all dependent rows. A confirmation step is shown before the delete executes.

Merging Duplicates

Requires users.edit. Merges two user records into one. Force-deleting the leftover duplicate pair record additionally requires the SUPER_ADMIN role.

Other Per-User Actions

  • UH Sync (single user) — compare this user's local data against the UH Directory API and resolve field differences. Requires users.edit.
  • Quick-sync a single field — AJAX refresh of one field from the upstream UH API without leaving the profile. Requires users.edit.
  • Fetch publications — trigger an on-demand ORCID or PubMed pull for this user. Requires users.edit.
  • Data quality exclusions — suppress known-acceptable DQ issues for this user. Requires users.edit.
  • LDAP lookup — search CougarNet AD to verify account state and external IDs. Requires users.view.
  • UH API person search — look up someone in the UH Directory API to pre-fill a new import. Requires users.edit.

Needs Attention View

A dedicated tab surfaces users carrying flags like Admin - Check or No UH. Visible with users.view; limited to your role scope.

4. User Media & Photos

Photo management lives under /admin/user-media/ and uses a three-step pipeline: source assignment, variant generation, then publishing.

Viewing

Requires media.view. You can see the published image count, which users have unpublished variants waiting, and browse individual user photo statuses.

Managing Sources & Variants

Requires media.edit. You can assign a Dropbox path or upload as a user's source image, trigger variant generation per variant type, and initiate bulk image transfers from Dropbox.

Publishing

Requires media.publish. Moves generated variant files from the temp directory to the public /_published_images/ folder and updates the live image URLs in the database.

Unpublishing

Requires media.unpublish. Removes an image from public availability without deleting the variant record.

Variant configuration (defining variant type names, dimensions, and processing modes) is separate and requires settings.media_config.manage under Settings.

5. UserReview Submissions

UserReview is the self-service flow where directory users submit proposed profile changes that an admin must approve before they go live. The admin side lives under /admin/user-review/.

Reviewing Submissions

Requires users.approve_user_review. You can see all pending and recently reviewed submissions, approve or reject an entire submission, or resolve individual fields within a submission. Discarding a field requires a written reason that is surfaced back to the submitter.

Configuring UserReview

Requires settings.user_review.manage. You can enable or disable the UserReview feature, configure which user flag types are eligible to submit, and adjust form field availability settings.

Having only one of the two permissions narrows the UserReview settings page to just what you can act on. Having both shows the full combined view.

6. Directory Structure

The organizational building blocks of the directory — flags, organizations, and external system definitions — each have their own gated admin areas.

Flags

Managed at /admin/settings/flags/. Requires flags.manage. You can create, edit, reorder, and retire flag definitions. The Protected setting on a flag controls whether it is hidden from API responses unless the caller presents a valid secret. Flag names are referenced directly by the scoped-role system, so renames affect access control.

Organizations

Managed at /admin/settings/orgs/. Requires orgs.manage. You can create, edit, reorder, and retire organizations. The parent-org relationship defines the hierarchy shown in the API and browsing views. Organization names are referenced by scoped roles, so renames affect which users those roles can access.

External Systems

Managed at /admin/settings/external/. Requires external_ids.manage. External systems are the labels (e.g., CougarNet, PeopleSoft) attached to external ID values stored per user. Creating or editing system definitions here affects how external IDs are displayed and resolved throughout the app.

7. Reporting

Reports are accessible from the /admin/reporting/ area and from the dashboard. Most reports are read-only views of data that is populated by scheduled or manually triggered jobs.

Report What it Shows Gate
Data Quality Missing fields, duplicate emails/IDs, invalid org/flag assignments, and other per-user issues from the most recent audit run. Accessible to all authenticated admins (admin.view).
UH Sync Field-by-field differences between local records and the UH Directory API from the most recent sync run, plus records that have disappeared or newly appeared upstream. settings.uh_sync.view
Duplicate Users Candidate pairs of user records that appear to be the same person, with a merge action. SUPER_ADMIN role only.

Running Reports Manually

Data Quality and UH Sync reports have a "Run Now" button that triggers a fresh job in-process. The same jobs can be scheduled through the ColdFusion Scheduler. Running them manually requires the same permission as viewing the report. The duplicate scan is triggered from the Duplicate Users report page and is also SUPER_ADMIN-only.

Role-Only Gates

Two capabilities are checked against the role directly rather than a permission key, and cannot be granted via per-user permission overrides:

  • SUPER_ADMIN role — duplicate users report, force-deletion of duplicate pair records, impersonation of other admin users, and direct triggering of certain scheduled tasks.
How gates are enforced: every admin page checks permissions at the top of the file using request.hasPermission() or application.authService.hasRole(). A failed check immediately redirects to /admin/unauthorized.cfm. The navigation sidebar also hides links to sections you cannot access, so most users will never encounter an unauthorized page in normal use.
