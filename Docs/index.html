1. Overview

UHCO Ident is the authoritative directory application for UHCO faculty, staff, current students, and alumni. It centralizes roster management, syncs with the university-wide UH Directory API, and exposes its own secured REST API for downstream systems such as Modern Campus and the MyUHCO portal.

Technology Stack

  • Back end: Adobe ColdFusion, developed on CF2025 and deployed on CF2021
  • Database: Microsoft SQL Server via datasource UHCO_Identity_Admin
  • Front end: Bootstrap 5 and Bootstrap Icons in the admin; SCSS compiled to /assets/css/
  • Web server: IIS with URL Rewrite for API routing
  • External integration: UH Directory API (Bearer + HMAC) and CougarNet LDAP for authentication
  • Dropbox integration for user photo management
  • Self-service workflow: UserReview staged profile updates with admin approval

Application URL Structure

  • /admin/ administrative back-office
  • /UserReview/ end-user self-service review experience
  • /api/v1/ REST API endpoints
  • /assets/ compiled CSS and JS (SCSS source in /assets/scss/)
  • /model/services/ service-layer CFCs (mapped as /cfc)
  • /model/dao/ DAO-layer CFCs (mapped as /dao)
  • /model/includes/ shared helper partials (mapped as /includes)
  • /sql/ schema and migration scripts
  • /_published_images/ photo publishing target directory
  • /_temp_variants/ image variant working directory

2. Core Data Model

All data is stored in SQL Server and hangs off the central Users table. The model is a star pattern with user identity at the center and related records branching by concern.

Primary User Fields

Name fields: FirstName, LastName, and related name parts are no longer stored directly on Users. All names are stored in UserAliases and resolved at query time by nameResolution_service.cfc. See Section 5 for details.

3. Admin Authentication & RBAC

Admin authentication is handled by admin/AuthService.cfc (the in-memory session object) backed by ldapAuthGateway_service.cfc for credential validation and adminAuth_DAO.cfc for role/permission persistence.

Login Methods

  • CougarNet (LDAP): username and password validated against the CougarNet Active Directory. This is the primary login method.
  • Windows SSO: implemented in auth_windows_start.cfm / auth_windows_callback.cfm but disabled by application.flags.windowsSSOEnabled = false until the production server has IIS Windows Authentication installed.

Session & Authorization Helpers

On every admin request, onRequestStart in Application.cfc attaches these helper closures to request:

  • request.hasRole(roleName)
  • request.hasPermission(permissionKey)
  • request.hasAnyPermission([])
  • request.isImpersonating()
  • request.canManageTestUsers()
  • request.canAccessUser(flags, orgs)

Role-Based Access Control

Roles are stored in AdminRoles and assigned to AdminUsers. Permissions are string keys attached to roles. The adminAuthorizationPolicy_service.cfc enforces scoped user-record visibility per role.

Admin User Management

Admin users are created and managed at admin/settings/admin-users/. Roles are managed at admin/settings/admin-roles/. Permissions are attached to roles at admin/settings/admin-permissions/. Per-user permission overrides (grants or denials outside a role) are managed at admin/settings/user-permissions/.

Impersonation & Test Mode

SUPER_ADMIN can impersonate any admin user for testing. Test Mode (toggled in App Config settings) enables a set of synthetic test-user records that are invisible to all non-SUPER_ADMIN roles. Test users can be generated, reset, or deleted from admin/settings/app-config/.

4. User Management

The admin/users/ area is the core administrative workspace. The app treats five user groupings as first-class admin views: Faculty, Staff, Current Students, Alumni, and Inactive.

User List

  • Paginated, sortable table with filters driven by tabs and query-string state.
  • Dedicated "Needs Attention" view for records carrying flags such as Admin - Check or No UH.
  • Scoped admin roles see only the users their role permits (enforced by adminAuthorizationPolicy_service.cfc).
  • Test users are filtered out for all roles except SUPER_ADMIN.

User Profile View

The profile view uses directory_service.getFullProfile(userID) and renders identity, resolved aliases, contact info, titles, photo gallery, organizations, flags, external IDs, addresses, academic info, bio, publications, degrees, sync history, and data-quality exclusions.

Create, Edit, Delete

  • new.cfm creates a minimal user record (limited required fields).
  • edit.cfm uses the same save flow with existing data; name parts are written to UserAliases, not directly to Users.
  • saveUser.cfm delegates to userEditSave_service.cfc which orchestrates alias, contact, org, and flag writes in a single transaction-aware flow.
  • Delete uses userDeletion_service.cfc, which hard-deletes the user and cleans dependent rows.
  • merge.cfm merges two duplicate user records; candidate pairs are surfaced by the duplicate report.

Per-User UH API Sync

Admins can sync a single user from the UH Directory API via resolve_uh_sync_diff.cfm and resolve field-by-field differences. A lightweight AJAX endpoint at quick_sync_field.cfm refreshes a single field from the upstream source without leaving the profile view.

Publications Fetch

An AJAX endpoint at fetchPublications.cfm triggers an on-demand pull of ORCID or PubMed publications for a user. See Section 9.

LDAP Lookup

search_UH_LDAP.cfm provides a direct CougarNet LDAP search tool for looking up people by samAccountName, display name, or email. Useful for finding external IDs and verifying account state before importing.

5. User Names & Aliases

Names are no longer stored as direct columns on Users. Every user has one or more rows in UserAliases, each with an AliasType (e.g., Primary, Preferred, LDAP, UH API). The primary alias is the canonical display name used throughout the admin and API.

Alias Record Structure

  • AliasID
  • UserID
  • AliasTypeID (references AliasTypes)
  • FirstName, MiddleName, LastName
  • IsPrimary — exactly one per user

Resolution Services

  • aliases_service.cfc — CRUD for alias records.
  • nameResolution_service.cfc — bulk resolves name data for arrays of user rows returned by any DAO, attaching FIRSTNAME, LASTNAME, FULLNAME, etc. All list pages and API responses go through this service.
Why aliases: the system now integrates with both LDAP (where names come from AD attributes) and the UH API (which may supply a different display name). Aliases allow all name sources to coexist per user without overwriting the canonical record.

6. UserReview Workflow

UserReview is a separate self-service flow that allows eligible users to stage profile changes without writing directly to the live Users record. Changes remain pending until an authorized admin approves or rejects them.

User Experience

  • Public entry point lives under /UserReview/ with its own login and session namespace.
  • Eligibility is based on feature settings plus user flags such as Faculty and Staff, not the admin-role system.
  • Title1 and EmailPrimary are shown read-only and cannot be edited.
  • Existing secondary emails, phones, and addresses are preloaded to prevent duplicate entry.
  • Plain @uh.edu addresses are excluded from editable secondary email rows; @central.uh.edu and @cougarnet.uh.edu are allowed.

Submission Lifecycle

  1. User loads the form model from live profile data plus any unresolved pending changes.
  2. Only actual diffs are stored; unchanged contact collections are ignored.
  3. Submission data is written to UserReviewSubmissions and UserReviewSubmissionFields.
  4. Admins may approve or discard an entire submission or resolve individual fields.
  5. Approved fields update live data immediately.
  6. Status becomes approved, rejected, or partially_approved after all fields are resolved.

Authentication

UserReviewAuthService.cfc authenticates users against the CougarNet LDAP (same gateway as the admin login). It also supports an external token flow (externalAuthToken + cougarnetID + launchContextToken) for integrations such as the MyUHCO portal that need to launch UserReview on behalf of an already-authenticated user without re-prompting for credentials.

Review Notes

Discard actions require a reason. Notes are appended to UserReviewSubmissions.ReviewNote, shown on the admin review page, and surfaced back to the user when the most recent reviewed outcome is rejected or partially_approved. A new pending submission suppresses the prior review-update alert until the new submission is reviewed.

Key Files

  • UserReview/index.cfm, login.cfm, authenticate.cfm, save.cfm, layout.cfm
  • model/services/UserReviewAuthService.cfc — end-user authentication, LDAP credential validation, external token flow
  • model/services/userReview_service.cfc — form modeling, diffing, and approval logic
  • model/dao/UserReview_DAO.cfc — submission persistence and review-state queries
  • admin/settings/user-review/ — admin configuration, submission queue, review UI, and approval endpoints

7. User Media & Photos

The admin/user-media/ section manages user profile photos through a three-stage pipeline: source images are pulled from Dropbox (or uploaded directly), processed into typed variants, and then published to /_published_images/.

Image Pipeline Stages

  1. Source assignment — each user is linked to a source image via UserImageSources. Sources can be a Dropbox path, a local upload, or a URL.
  2. Variant generation — admins trigger explicit generation per variant type. UserImageVariantService.cfc and ImageProcessor.cfc produce the output file in /_temp_variants/.
  3. Publishing — PublishingService.cfc moves the approved variant files to /_published_images/ and updates UserImages with the public URLs. The published base URL is configurable via App Config (media.published_site_base_url).

Variant Types & Modes

Variant types define the target dimensions and processing mode. Three modes are supported:

  • Resize — scales to target width/height
  • Resize and Crop — scales then center-crops to exact dimensions
  • Pass-through — copies the source file as-is (JPG, PNG, or WebP)

Variant types are managed at admin/settings/media-config/variant-types.cfm. Filename patterns for published images are configured at admin/settings/media-config/filename-patterns.cfm.

Dropbox Integration

DropboxProvider.cfc obtains a short-lived Dropbox access token using the OAuth2 refresh-token flow. Credentials (dropbox.app_key, dropbox.app_secret, dropbox.refresh_token) are stored in App Config. Tokens are cached in server scope and refreshed automatically on expiry.

Variant Lifecycle States

StateMeaning
missingVariant type exists but no record yet — source must be assigned first.
staleRecord exists but source changed or was just assigned — generation available, not automatic.
currentGenerated successfully; source unchanged. No action required.
errorLast generation failed — error message stored; re-generation allowed.

Bulk Operations

admin/user-media/bulk-transfer.cfm uses BulkImageTransferService.cfc to transfer source images in batch from Dropbox to local storage. A health endpoint at admin/user-media/health.cfm shows overall publishing status counts.

Permissions

  • media.view — view published images and variant status across users
  • media.edit — assign sources, trigger generation, and publish variants

8. Bio

Each user can have a rich-text biographical profile stored in UserBios. Bio content is authored in the admin profile editor using a Quill-based rich text control and sanitized server-side before storage.

Sanitization Rules

bio_service.sanitizeHTML() applies a whitelist policy: only <p>, <strong>, <em>, <a>, <ul>, <ol>, <li>, and <br> are kept. All attributes are stripped except href and target on anchors. javascript: and data: URIs in href are blocked.

API Access

Bio content is available at GET /api/v1/people/{id}/bio. The response includes raw HTML and a plain-text excerpt.

9. Publications

Faculty members can have academic publications pulled from ORCID and PubMed and displayed in the directory. A subset of publications can be marked as showcased and exposed via the API.

Data Sources

  • ORCID — publicationProvider_orcid.cfc fetches works using the researcher's ORCID iD (stored in UserExternalIDs).
  • PubMed — publicationProvider_pubmed.cfc searches by author name or NLM ID.

Fetch & Merge Flow

  1. Admin triggers fetch via admin/users/fetchPublications.cfm (AJAX, returns JSON).
  2. publicationFetch_service.cfc calls the configured providers and collects raw records.
  3. publicationMerge_service.cfc de-duplicates across sources and inserts or updates Publications and PublicationSourceRecords.
  4. A PublicationFetchRuns record is written with counts and timestamp.

Configuration Keys (App Config)

  • publications.max_showcased_per_user — maximum showcased publications per user (default 10).
  • publications.faculty_flags — comma-separated flag names for publication-eligible users (default: Faculty-Adjunct, Faculty-Fulltime, Professor-Emeritus, Joint Faculty Appointment).

Tables

Publications (merged deduplicated records), PublicationProfiles (per-user provider settings including ORCID iD), PublicationSourceRecords (raw per-source hits), PublicationFetchRuns (fetch audit log).

10. Organizations

Organizations provide the hierarchy used for browsing, filtering, and representing the college's internal structure.

Structure

  • OrgID, OrgName, OrgAbbr
  • ParentOrgID supports a self-referential tree
  • OrgType controls display grouping
  • SortOrder controls sequence
  • Active hides retired orgs from display and API output

User Assignments

UserOrganizations allows multiple org memberships per user with start and end dates. Admin pages support add/remove membership management directly from the user profile. The OD Program, PhD Program, MS Program, Clinical Sciences, Optometry Clinic, and Vision Science org names are referenced by the scoped-role system.

11. Flags

Flags are used for filtering, admin workflows, scoped-role access control, and API data protection.

Definition Model

  • FlagID, FlagName, FlagDescription
  • Protected marks flags that require a valid secret to be returned in API responses
  • SortOrder and Active control display and retirement behavior
Protected data behavior: flags such as Current-Student and Alumni are filtered from API responses unless the caller presents a valid secret that unlocks those protected flags. The scoped-role system also uses flag names directly (e.g., Faculty-Adjunct, Staff, Current-Student) to determine which users a given admin role may access.

People Query Parameters

  • flag filter by flag name
  • org filter by organization ID
  • class filter by academic cohort year
  • limit max 500, default 50
  • offset pagination offset
  • format json or xml

Token Validation Pipeline

  1. Authorization header is present and correctly formatted.
  2. SHA-256 hash of the token matches a stored record.
  3. Token is not revoked.
  4. Token is not expired.
  5. Caller IP satisfies allowlist or CIDR rules.
  6. Requested scope is permitted.
  7. LastUsedAt is updated on success.

Error Format

{ "error": "message", "status": 401 }

CORS

CORS headers are set in the API sub-application's Application.cfc. The allowed origin is configurable to support browser-side integrations (e.g., MyUHCO portal).

Utility Endpoints

  • GET /api/v1/access?userID={id} — returns the effective permissions for a given admin user ID.
  • GET /api/v1/permission-roster?permission={key} — returns the list of admin users who hold a given permission key.

14. Tokens and Secrets

API tokens and secrets are managed separately because they solve different security problems.

Tokens

  • Grant API access
  • Store only SHA-256 hashes, never the raw token
  • Track scope, allowlist, expiration, revocation, and last used time
  • Can be revoked or permanently deleted
  • Managed at admin/settings/uhco-api/tokens/

Secrets

  • Unlock protected flag and organization data in API responses
  • Also store only SHA-256 hashes
  • Define which protected flags a client may see
  • Use the same one-time reveal lifecycle as tokens
  • Managed at admin/settings/uhco-api/secrets/

Quick Test Credential Generator

A built-in tool in the API settings area generates short-lived test tokens and secrets for development and integration testing without creating permanent credentials.

15. App Config

appConfig_service.cfc provides a database-backed key/value store accessed throughout the application for runtime configuration. Values are stored in the AppConfig table and retrieved by key. Sensitive keys (LDAP credentials, Dropbox secrets, etc.) are encrypted at rest using AES with a key derived from the UHCO_IDENT_APPCONFIG_ENC_KEY OS environment variable.

Encryption Policy

runtimeSecretPolicy_service.cfc enforces that encryption is active in non-local environments. On every request, Application.cfc checks the health status; if encryption is required but the key is absent, a warning is logged and the app continues in a degraded-security state rather than crashing.

16. UH Directory Sync

UHCO Ident maintains its own copy of staff and faculty data and periodically compares it against the upstream UH Directory API.

Credentials and Configuration

  • UH_API_TOKEN Bearer token — OS environment variable, loaded into application scope at startup via runtimeSecretPolicy_service.cfc.
  • UH_API_SECRET HMAC signing secret — same source.

Bulk Sync Flow

  1. Load all local users with a non-null UH_API_ID.
  2. Retrieve current staff and faculty from the UH API.
  3. Build a lookup keyed by UH_API_ID.
  4. Compare each local record field by field.
  5. Write differences to UHSyncDiffs.
  6. Track local-only records in UHSyncGone.
  7. Track upstream-only people in UHSyncNew.
  8. Create a UHSyncRun record with counts and metadata.

Reporting

Sync results are reviewed at admin/reporting/uh_sync_report.cfm. The admin/users/uh_people_db_not_in_api.cfm report finds local records whose UH_API_ID no longer appears upstream. The dashboard shows a pending-changes badge driven by the most recent UHSyncRun.

17. Data Quality

The data-quality system audits the local database for missing or inconsistent information and stores findings for review.

Typical Issue Codes

NO_EMAIL NO_PHONE NO_ROOM NO_BUILDING NO_TITLE NO_DEPT NO_ORG NO_FLAG NO_PHOTO NO_UH_ID DUP_EMAIL DUP_UH_ID INACTIVE_ORG INACTIVE_FLAG NO_ACADEMIC NO_GRAD_YEAR MISSING_PREFERRED

Excluded issues can be suppressed per user via DataQualityExclusions when a known exception is acceptable. Exclusions are managed from the user profile view at admin/users/saveDQExclusions.cfm.

Duplicate Users Report

A separate report at admin/reporting/duplicate_users_report.cfm scans for candidate duplicate user records (same name, email, or external ID). Results are stored in DuplicateUserPairs. The dashboard shows a pending-pair count badge visible only to SUPER_ADMIN. Confirmed duplicates can be merged via admin/users/merge.cfm.

18. Bulk Tools and Reporting

The admin area contains recurring import, audit, and migration utilities beyond sync and data quality.

Import Tools (admin/settings/import/)

  • CSV Bulk Import: mass-creates new users with initial org and flag assignments from an uploaded spreadsheet.
  • Alumni Bulk Import: creates alumni records with graduation metadata.
  • UH People Import (admin/users/uh_people_import.cfm): interactive import of people found in the UH Directory API but not yet in the local database.

Roster Tools (admin/settings/rosters/)

Upload and compare enrollment rosters (e.g., OD cohort lists) against the current directory to identify additions and departures.

Grad Migration (admin/settings/migrations/)

gradMigration_service.cfc runs a configurable graduated-student migration that transitions current students to alumni status, applies graduation-year flags, and can optionally deactivate departed records. The migration runs inside a ColdFusion transaction for atomicity. Auto-execute mode and a scheduled trigger are supported. Requires the settings.migrations.manage permission.

Query Builder (admin/settings/query-builder/)

An admin-only ad hoc query tool backed by queryBuilder_service.cfc. Provides a safe parameterized interface for running pre-approved queries against the directory database for data analysis.

Bulk Image Transfer (admin/user-media/bulk-transfer.cfm)

Scans Dropbox for source images matching user records and transfers them in batch to local storage. Filters by user type to avoid overwriting unrelated source images.

19. Admin Interface & Settings

The admin side is a server-rendered Bootstrap application with shared layout, dashboard, reporting pages, and operational utilities. All CSS is compiled from SCSS in assets/scss/admin.scss and served from assets/css/admin.css.

Dashboard

admin/dashboard.cfm shows status badges for Data Quality, UH Sync, and (for SUPER_ADMIN) Duplicate Users. Each badge links to the relevant report. Stale-month and list-page-size thresholds are configurable through App Config.

All settings pages live under admin/settings/ and are protected by granular permission checks. Scheduled tasks are defined in admin/settings/scheduled-tasks/tasks/. Each task file includes _scheduled_task_auth.cfm which validates a shared secret before executing, preventing unauthorized direct HTTP calls to the task endpoint.

Operational Pages

  • admin/diagnostic.cfm — surfaces runtime environment, datasource connectivity, and credential health.
  • admin/clear_cache.cfm and admin/resetapp.cfm — maintenance pages for cache and application-scope reset.
  • admin/access/ — manages named access areas used for fine-grained feature gating.
  • admin/external/ — manages external system definitions referenced by UserExternalIDs.

20. Architecture and Code Structure

UHCO Ident uses a three-layer design with request-time object creation and no dependency injection framework.

Layer Overview

  • Presentation: .cfm pages in admin/ and api/v1/
  • Service: CFCs in model/services/ (mapped as /cfc)
  • Data access: CFCs in model/dao/ (mapped as /dao), all extending BaseDAO.cfc

Instantiation Pattern

<cfset svc = createObject("component",
    "cfc.users_service").init()>

The /cfc and /dao mappings in Application.cfc resolve to model/services/ and model/dao/ respectively, so all existing instantiation calls continue to work without path changes.

BaseDAO Utilities

  • executeQueryWithRetry(sql, params, options) — retries transient connection errors with backoff.
  • queryToArray(query) — normalizes ColdFusion query results into uppercase-key structs.

Application Scope

Application.cfc initializes several singletons on startup:

  • application.authService — admin/AuthService.cfc, the in-memory session-aware admin auth object.
  • application.userReviewAuthService — UserReviewAuthService.cfc, end-user session for the UserReview flow.
  • application.adminAuthorizationPolicyService — adminAuthorizationPolicy_service.cfc, scoped user-record access enforcement.
  • application.runtimeSecretPolicyService — runtimeSecretPolicy_service.cfc, centralizes retrieval of OS env secrets and encrypted AppConfig values.
  • application.uhApiToken / application.uhApiSecret — loaded via runtimeSecretPolicyService from OS environment variables.

Request Context Routing

onRequestStart sets request.context to "userreview" for any path beginning with /userreview/ and to "admin" otherwise. The UserReview context uses the separate user-auth session; the admin context attaches role/permission helpers and enforces admin login.

API Sub-Application

The API lives in api/v1/Application.cfc as a child application. Sessions are disabled. Unhandled errors are caught and returned as JSON 500 responses. CORS headers are applied per request. The IIS rewrite rule routes all /api/v1/* requests to /api/v1/index.cfm as a _path query parameter.

Assets / SCSS Build

Styling is managed in assets/scss/ with three entry points: admin.scss, userreview.scss, and api-docs.scss. Compiled output goes to assets/css/. Bootstrap 5 and Bootstrap Icons are vendored in assets/vendor/. The assets/js/ folder holds per-section JavaScript, including api-docs-quick-auth.js for the interactive auth helper on the API docs page.

21. Deployment and Security

Required Configuration

  • Set OS-level environment variables UH_API_TOKEN and UH_API_SECRET.
  • Set UHCO_IDENT_APPCONFIG_ENC_KEY in non-local environments (required for AppConfig encryption of sensitive keys).
  • Configure the ColdFusion datasource UHCO_Identity_Admin.
  • Install the IIS rewrite rule that routes /api/v1/* to /api/v1/index.cfm.
  • Schedule UH Sync, Data Quality, and Grad Migration tasks through the ColdFusion Scheduler, pointing to task files in admin/settings/scheduled-tasks/tasks/.
  • Run schema scripts in sql/ including UserReview, alias, bio, publications, image variant, app config, and admin auth tables.
  • Seed admin roles and grant SUPER_ADMIN to the initial admin account via admin/settings/admin-roles/ and admin/settings/admin-users/.
  • Configure auth.ldap.server and LDAP bind credentials in App Config.
  • Configure Dropbox OAuth2 credentials in App Config if using the photo pipeline.

Compatibility Notes

  • Developed on ColdFusion 2025 and compatible with ColdFusion 2021.
  • queryExecute return type support, arraySort() closure callbacks, and qry.getRow(1) are all supported on the deployed version line.
  • Windows SSO requires IIS Windows Authentication to be installed on the production server. It is currently disabled via application.flags.windowsSSOEnabled = false.

Security Checklist

  • Ensure UHCO_IDENT_APPCONFIG_ENC_KEY is set in production before storing any sensitive AppConfig values.
  • Restrict admin/ at the IIS or network level; the application-layer auth is the last line, not the only one.
  • Lock down admin/diagnostic.cfm to admins only (it exposes runtime and credential health).
  • Enforce HTTPS for all admin and API traffic.
  • Review API token IP allowlists and rotate UH API credentials periodically.
  • Rotate Dropbox OAuth2 credentials if the refresh token is compromised.
